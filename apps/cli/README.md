# `@egeria-systems/cli`

Private command adapter for the Egeria Systems builder kernel.

The approved boundary contains ten exact commands: `create`, `infer`, `doctor`, `diff`, `plan-add`, `apply-add`, `plan-remove`, `apply-remove`, `plan-upgrade`, and `apply-upgrade`. `apply-remove` is the exact current removal command; `plan-upgrade` is read-only. The executable performs strict command-specific argument parsing, delegates all builder policy and repository behavior to private `@egeria-systems/builder-core`, and emits one content-safe JSON line with stable exits.

`create` generates only a previously absent portfolio or site directory through the verified state-last builder-core boundary. It accepts either the exact base creation arguments or those arguments plus paired `--calendly-url` and `--calendly-mode` options for explicit Calendly initial scaffolding. The mode is exactly `link`, `inline`, or `popup`; builder-core owns the bounded HTTPS Calendly destination contract, selected-capability/settings agreement, and sanitized validation issues.

`infer`, `doctor`, and `diff` are read-only and evaluate the declared Calendly surfaces and settings through builder-core when installed. `plan-add` is also read-only: for a clean attached linked worktree, it checks current project health and returns a deterministic, redacted approval-required plan for adding `booking-calendly@0.1.0`. It detects tracked changes, all non-ignored untracked files, and the `assume-unchanged` and `skip-worktree` index flags. It requires exact canonical managed-surface inventory and installed application-owned paths to remain files without comparing their content fingerprints. It refuses managed drift, ejections, present collisions, absent but ignored create targets, operations, conflicts, detached or primary worktrees, unexpected Git/reader failures, and a changed final Git identity. It never creates the worktree or branch and performs no transform, migration, state update, dependency installation, or provider action.

`plan-remove` is also read-only and supports only exact installed `booking-calendly@0.1.0` in the current `portfolio` and `site` recipes. Between two matching clean linked-worktree inspections, builder-core requires exact desired, installed, inferred, inventory, and ejection agreement; refuses managed or shared-composition drift; and returns path-sorted actions that delete unchanged capability files, replace the shared home route and project configuration, or preserve modified/already-ejected application files as `preserve-file-and-eject`. Every plan also contains a fingerprint-bound repository-wide surviving-reference review requirement; when an application-owned file is preserved/ejected, a second requirement lists its exact path for reconciliation before transformation approval. This is an explicit operator/agent review contract, not an arbitrary-source scanner. The public plan redacts settings and Git metadata except for the intentional base revision while its fingerprint binds the full private project, state, actions, review requirements, and Git identity. A clean repository without the capability returns exact `CAPABILITY_NOT_INSTALLED`. Planning performs no deletion, replacement, ejection, verification, migration append, state write, dependency change, or provider action.

`plan-upgrade --directory <absolute-existing-linked-worktree> --capability standards --to-version 0.4.0` is the first read-only supported-upgrade boundary. It accepts no `--from-version`. Builder-core infers exact installed `standards@0.3.0`, resolves only the declared edge to `0.4.0`, and requires matching recipe `0.9.0` provenance plus desired, installed, version-specific inference, project, state, migration, and canonical surface-inventory agreement. The fingerprint binds the accepted endpoint subjects, exact SHA-256 evidence for `project.yaml`, `state.json`, and `migrations.jsonl`, six target actions and their fingerprints, and private Git identity without returning project copy, absolute paths, branch names, or Git directories. Already-current, missing-edge, ambiguous-version, drift, ejection, incompatible-state, collision, dirty, detached, primary-worktree, operation, conflict, and unstable-identity cases return one stable stderr JSON line without mutation. The command performs no transformation, generated verification, migration, state persistence, upgrade execution, dependency installation, or provider action.

`apply-add` accepts the same paired Calendly settings plus the exact `sha256:` plan fingerprint. Builder-core recomputes that plan in the same clean linked worktree, writes only its seven actions, verifies a separate copy, re-infers, appends one successful migration record, writes state last, re-infers again, and requires the exact expected dirty paths. Success stops at `verified-final-diff-approval-required`. Failures return only a stable phase and either `not-required` or `inspect-worktree` recovery; the CLI never resets, cleans, commits, creates the worktree or branch, contacts Calendly, or rolls a partial prefix back automatically.

`apply-remove --directory <absolute-existing-linked-worktree> --capability booking-calendly --approved-plan sha256:<digest>` accepts no Calendly settings. Builder-core recomputes the exact accepted removal plan and fingerprint in the same clean, stable, attached linked worktree, executes one ownership-aware batch that can delete, replace, preserve, and eject only planned surfaces, verifies a separate copy, re-infers before persistence, and completes migration append followed by state-last persistence. It then requires exact final desired/installed/inferred agreement, exact control-file bytes, preservation of modified or already-ejected application-owned surfaces, and the exact final Git diff before returning `verified-final-diff-approval-required`; that result is evidence awaiting verified-final-diff approval. A repeat removal returns exact `CAPABILITY_NOT_INSTALLED` without mutation. Failures before a write require no recovery; failures after a write retain the isolated-worktree prefix for inspection rather than rolling it back automatically.

`apply-upgrade --directory <absolute-existing-linked-worktree> --capability standards --to-version 0.4.0 --approved-plan sha256:<digest>` has exactly those four arguments and accepts no `--from-version`. It consumes only the exact approved `plan-upgrade` fingerprint for the single `standards@0.3.0` to `standards@0.4.0` edge. Builder-core recomputes the complete plan and stable Git identity immediately before its upgrade-specific six-action write, transforms once, runs ordinary verification, freshly infers, appends migration `upgrade-standards-0-3-0-to-0-4-0`, persists state last, proves final state/inference/migration agreement and the exact eight-path diff, and returns `verified-final-diff-approval-required`. Planning approval, execution, verification, persistence, recovery, and verified-final-diff approval remain separate. A failure after a committed write retains its inspectable prefix and never triggers automatic rollback.

The CLI has no prompt, overwrite mode, generic existing-repository mutation, second upgrade edge, profile transition, lifecycle extraction, deployment, publication, Calendly account configuration, provider API, provider-data ownership, credential handling, or persistent-data cleanup behavior. Local creation, inspection, planning, and the exact Calendly and standards transactions do not establish final-diff approval, automated recovery, lifecycle certification, deployed behavior, provider behavior, performance or visual quality, security clearance, production readiness, human accessibility, or WCAG conformance.

The canonical API and lifecycle owner is [package ownership](../../docs/architecture/package-ownership.md).
