# `@egeria-systems/cli`

Private command adapter for the Egeria Systems builder kernel.

The approved boundary contains ten exact commands: `create`, `infer`, `doctor`, `diff`, `plan-add`, `apply-add`, `plan-remove`, `apply-remove`, `plan-profile-transition`, and `apply-profile-transition`. Planning is read-only; every apply command is fingerprint-gated. The adapter delegates builder policy and emits one content-safe JSON line with stable exits.

Unused public generations, capability-upgrade commands and old profile-transition edges are retired under [ADR-0020](../../docs/adr/0020-application-environments.md#early-retirement-of-unused-public-generations). Historical evidence remains preserved; unsupported controls refuse before effects. [ADR-0015](../../docs/adr/0015-vitest-five-generation.md#patched-public-generation) owns the exact current dependency and recipe tuples.

New creation selects `portfolio@0.11.7`, `site@0.12.7`, or `app@0.2.7` under [ADR-0015](../../docs/adr/0015-vitest-five-generation.md). The default app composes `app-foundation@0.1.0 + site-routing@0.4.0`, retaining the complete production-site experience from [ADR-0013](../../docs/adr/0013-convergent-app-profile.md). Direct `effect@4.0.0-rc.112` belongs only to generated server modules under [ADR-0014](../../docs/adr/0014-selective-effect-application-runtime.md); the CLI remains Effect-free. The [app lifecycle summary](../../README.md#app-lifecycle-and-verification) lists current edges, optional-subset coverage, unsupported operations, and separate recovery domains. The [enforcement map](../../docs/architecture/enforcement-map.md) names verification owners, and the [lifecycle protocol](../../docs/governance/review-and-contribution.md) owns approval gates. Current certification follows the [capability model](../../docs/architecture/capability-model.md#certification-coverage); invoking the CLI does not certify a subject.

`create` generates only a previously absent portfolio, site, or app directory through the verified state-last builder-core boundary. It accepts the exact base creation arguments, independent booleans `--multilingual`, `--transactional-email-resend`, `--background-job-delivery`, and app-only `--application-persistence`, paired `--calendly-url` and `--calendly-mode` options, strict public `--web3forms-access-key` for hosted contact, and strict analytics options for Cloudflare Web Analytics, Google Analytics 4, Microsoft Clarity, Google Search Console, and Looker Studio. The Calendly mode is exactly `link`, `inline`, or `popup`. Analytics requires at least one runtime provider or Search Console; Looker Studio requires GA4; and Clarity requires `--microsoft-clarity-audience not-directed-to-minors`. Builder-core owns selected-capability/settings agreement and sanitized validation issues. CLI output never returns provider identifiers.

`infer`, `doctor`, and `diff` are read-only and evaluate declared Calendly, multilingual, analytics, application-persistence, transactional-email, hosted-contact, and background-job-delivery settings/surfaces through builder-core when installed. `plan-add` is also read-only: for a clean attached linked worktree, it checks current project health and returns a deterministic, redacted approval-required plan for adding exact `booking-calendly@0.1.0` with paired settings, exact `multilingual@0.1.0` without settings, exact `analytics@0.1.0` with strict provider/operational settings, setting-free `application-persistence@0.1.1` for the supported app tuple, setting-free `transactional-email-resend@0.1.0` for current recipes, exact `contact-form-web3forms@0.1.0` with its strict public `--web3forms-access-key` setting, or setting-free `background-job-delivery@0.2.0` for the exact [jobs tuples](../../docs/architecture/capability-model.md#exact-jobs-lifecycle). It detects tracked changes, all non-ignored untracked files, and the `assume-unchanged` and `skip-worktree` index flags. It requires exact canonical managed-surface inventory and installed application-owned paths to remain files without comparing their content fingerprints. It refuses managed drift, ejections, present collisions, absent but ignored create targets, operations, conflicts, detached or primary worktrees, unexpected Git/reader failures, and a changed final Git identity. It never creates the worktree or branch and performs no transform, migration, state update, dependency installation, provider action, or identifier disclosure.

`plan-remove` is also read-only and supports exact installed `booking-calendly@0.1.0`, `multilingual@0.1.0`, `analytics@0.1.0`, `transactional-email-resend@0.1.0`, or `contact-form-web3forms@0.1.0` in the current `portfolio`, `site`, and `app` recipes, plus `application-persistence@0.1.1` for the supported app tuple and actual installed `background-job-delivery@0.1.0` or `0.2.0` for the exact jobs tuples. Jobs planning requires `--job-removal <absolute-json-path>` and returns its machine report; `--job-human-review` belongs only to application. Persistence planning requires `--persistence-removal <absolute-json-path>` and returns the machine review report with the source-removal plan. Between two matching clean linked-worktree inspections, builder-core requires exact desired, installed, inferred, inventory, and ejection agreement; refuses managed or shared-composition drift; and returns path-sorted actions that delete unchanged capability files, replace shared composition and project configuration, or preserve modified/already-ejected application files as `preserve-file-and-eject`. Every plan contains a fingerprint-bound repository-wide surviving-reference review requirement; analytics additionally requires explicit provider-account, retained-data, browser-storage, and cookie disposition review. The public plan redacts settings and Git metadata except for the intentional base revision while its fingerprint binds the full private project, state, actions, review requirements, and Git identity. A clean repository without the requested capability returns exact `CAPABILITY_NOT_INSTALLED`. Planning performs no deletion, replacement, ejection, verification, migration append, state write, dependency change, provider cleanup, or provider action.

Optional `application-persistence@0.1.1` also uses `plan-add`/`apply-add` and `plan-remove`/`apply-remove` for the exact app tuple. Its removal requires bounded evidence input, a machine review report produced by planning, and human review of the exact report and plan. The [persistence boundary](../../docs/architecture/capability-model.md#application-persistence-boundary) owns supported inputs, preservation, verification and separate provider/data recovery gates.

Optional transactional email preserves profile identity, adds its required foundation, and retains foundation after email removal. The CLI accepts no email addresses or credentials; runtime configuration and provider/key/retention dispositions remain separate. The [email boundary](../../docs/architecture/capability-model.md#transactional-email-boundary) owns exact supported tuples, verification and reviewed source-removal limits.

`apply-add` accepts the same paired Calendly settings, the exact setting-free multilingual subject, the same strict analytics selection, setting-free application persistence for the supported app tuple, setting-free transactional email for current recipes, hosted contact with its strict public `--web3forms-access-key` setting, or setting-free jobs `0.2.0` for the exact jobs tuples, plus the exact `sha256:` plan fingerprint. Builder-core recomputes that subject-specific plan in the same clean linked worktree, writes only its planned actions, verifies a separate copy, re-infers, appends one successful migration record, writes state last, re-infers again, and requires the exact expected dirty paths. Success stops at `verified-final-diff-approval-required`. Failures return only a stable phase and either `not-required` or `inspect-worktree` recovery; the CLI never resets, cleans, commits, creates the worktree or branch, contacts a provider, or rolls a partial prefix back automatically.

`apply-remove --directory <absolute-existing-linked-worktree> --capability <analytics|application-persistence|background-job-delivery|booking-calendly|contact-form-web3forms|multilingual|transactional-email-resend> --approved-plan sha256:<digest>` accepts no capability settings. Application persistence is restricted to the supported app tuple and additionally requires `--persistence-removal <absolute-json-path>` and `--persistence-human-review <absolute-json-path>` for bounded evidence and human dispositions of the exact machine report; `--approved-plan` binds the reviewed source-removal plan. Jobs removal additionally requires `--job-removal <absolute-json-path>` and `--job-human-review <absolute-json-path>` with fresh evidence and exact human dispositions; its complete form is `apply-remove --directory <absolute-existing-linked-worktree> --capability background-job-delivery --job-removal <absolute-evidence-json-path> --job-human-review <absolute-review-json-path> --approved-plan sha256:<digest>`. Builder-core recomputes the exact accepted subject-specific removal plan and fingerprint in the same clean, stable, attached linked worktree, executes one ownership-aware batch that can delete, replace, preserve, and eject only planned surfaces, verifies a separate copy, re-infers before persistence, and completes migration append followed by state-last persistence. It then requires exact final desired/installed/inferred agreement, exact control-file bytes, preservation of modified or already-ejected application-owned surfaces, and the exact final Git diff before returning `verified-final-diff-approval-required`; that result is evidence awaiting verified-final-diff approval. A repeat removal returns exact `CAPABILITY_NOT_INSTALLED` without mutation. Analytics source removal does not delete provider accounts, retained provider data, browser data outside the generated cleanup contract, or any external resource. Failures before a write require no recovery; failures after a write retain the isolated-worktree prefix for inspection rather than rolling it back automatically.

`plan-profile-transition --directory <absolute-existing-linked-worktree> --to-profile app` and `apply-profile-transition --directory <same-worktree> --to-profile app --approved-plan sha256:<digest>` support only current portfolio/site inputs targeting app. The parser recognizes `site`, but no supported edge targets it. Preserve clean stable linked-worktree checks, exact fingerprints, ownership/reference refusal, isolated verification, fresh inference, migration-before-state persistence and final agreement. Portfolio-to-app requires separate exact successor visual admission. Success remains `verified-final-diff-approval-required`; post-write failure retains the inspectable prefix.

The CLI has no prompt, overwrite mode, generic existing-repository mutation, undeclared upgrade or profile-transition edge, lifecycle extraction, deployment, publication, Calendly or analytics account configuration, provider API, provider-data ownership, credential handling, or persistent-data cleanup behavior. Local creation, inspection, planning, and the exact Calendly, multilingual, analytics, and incoming app transactions do not establish final-diff approval, automated recovery, lifecycle certification, translation quality, deployed behavior, provider behavior, privacy or legal compliance, performance or visual quality, security clearance, production readiness, human accessibility, or WCAG conformance.

The canonical API and lifecycle owner is [package ownership](../../docs/architecture/package-ownership.md).

Optional `create --background-job-delivery` supports current portfolio, site and app recipes independently of persistence and email. Exact `plan-add`/`apply-add` support jobs `0.2.0`; `plan-remove`/`apply-remove` derive installed `0.1.0` or `0.2.0` and require fresh `--job-removal` plus exact `--job-human-review` before application; see the [jobs boundary](../../docs/architecture/capability-model.md#background-job-delivery-boundary) for support and operator limits.
