# `@egeria-systems/cli`

Private command adapter for the Egeria Systems builder kernel.

The approved boundary contains twelve exact commands: `create`, `infer`, `doctor`, `diff`, `plan-add`, `apply-add`, `plan-remove`, `apply-remove`, `plan-upgrade`, `apply-upgrade`, `plan-profile-transition`, and `apply-profile-transition`. `plan-upgrade` and `plan-profile-transition` are read-only; each apply command is fingerprint-gated. The executable performs strict command-specific argument parsing, delegates all builder policy and repository behavior to private `@egeria-systems/builder-core`, and emits one content-safe JSON line with stable exits.

`create` generates only a previously absent portfolio or site directory through the verified state-last builder-core boundary. It accepts the exact base creation arguments, independent boolean `--multilingual`, paired `--calendly-url` and `--calendly-mode` options, or both optional selections together. The Calendly mode is exactly `link`, `inline`, or `popup`; builder-core owns the bounded HTTPS destination contract, selected-capability/settings agreement, strict multilingual selection, and sanitized validation issues.

`infer`, `doctor`, and `diff` are read-only and evaluate declared Calendly settings/surfaces and multilingual surfaces through builder-core when installed. `plan-add` is also read-only: for a clean attached linked worktree, it checks current project health and returns a deterministic, redacted approval-required plan for adding exact `booking-calendly@0.1.0` with paired settings or exact `multilingual@0.1.0` without settings. It detects tracked changes, all non-ignored untracked files, and the `assume-unchanged` and `skip-worktree` index flags. It requires exact canonical managed-surface inventory and installed application-owned paths to remain files without comparing their content fingerprints. It refuses managed drift, ejections, present collisions, absent but ignored create targets, operations, conflicts, detached or primary worktrees, unexpected Git/reader failures, and a changed final Git identity. It never creates the worktree or branch and performs no transform, migration, state update, dependency installation, or provider action.

`plan-remove` is also read-only and supports only exact installed `booking-calendly@0.1.0` or `multilingual@0.1.0` in the current `portfolio` and `site` recipes. Between two matching clean linked-worktree inspections, builder-core requires exact desired, installed, inferred, inventory, and ejection agreement; refuses managed or shared-composition drift; and returns path-sorted actions that delete unchanged capability files, replace shared composition and project configuration, or preserve modified/already-ejected application files as `preserve-file-and-eject`. Every plan also contains a fingerprint-bound repository-wide surviving-reference review requirement; when an application-owned file is preserved/ejected, a second requirement lists its exact path for reconciliation before transformation approval. This is an explicit operator/agent review contract, not an arbitrary-source scanner. The public plan redacts settings and Git metadata except for the intentional base revision while its fingerprint binds the full private project, state, actions, review requirements, and Git identity. A clean repository without the requested capability returns exact `CAPABILITY_NOT_INSTALLED`. Planning performs no deletion, replacement, ejection, verification, migration append, state write, dependency change, or provider action.

`plan-upgrade --directory <absolute-existing-linked-worktree> --capability standards --to-version 0.4.0` is the first read-only supported-upgrade boundary. It accepts no `--from-version`. Builder-core infers exact installed `standards@0.3.0`, resolves only the declared edge to `0.4.0`, and requires matching recipe `0.9.0` provenance plus desired, installed, version-specific inference, project, state, migration, and canonical surface-inventory agreement. The fingerprint binds the accepted endpoint subjects, exact SHA-256 evidence for `project.yaml`, `state.json`, and `migrations.jsonl`, six target actions and their fingerprints, and private Git identity without returning project copy, absolute paths, branch names, or Git directories. Already-current, missing-edge, ambiguous-version, drift, ejection, incompatible-state, collision, dirty, detached, primary-worktree, operation, conflict, and unstable-identity cases return one stable stderr JSON line without mutation. The command performs no transformation, generated verification, migration, state persistence, upgrade execution, dependency installation, or provider action.

The same command surface also declares exactly `plan-upgrade --capability site-routing --to-version 0.4.0` for `site@0.10.0` with installed `site-routing@0.3.0`. Its fingerprint binds the exact 22-action `site@0.11.0` target, including route, content, navigation, metadata, crawl-output, browser-test, framework, lockfile, project, migration, and state subjects. It refuses every other recipe/version pair and performs no write.

`apply-add` accepts either the same paired Calendly settings or the exact setting-free multilingual subject plus the exact `sha256:` plan fingerprint. Builder-core recomputes that subject-specific plan in the same clean linked worktree, writes only its planned actions, verifies a separate copy, re-infers, appends one successful migration record, writes state last, re-infers again, and requires the exact expected dirty paths. Success stops at `verified-final-diff-approval-required`. Failures return only a stable phase and either `not-required` or `inspect-worktree` recovery; the CLI never resets, cleans, commits, creates the worktree or branch, contacts a provider, or rolls a partial prefix back automatically.

`apply-remove --directory <absolute-existing-linked-worktree> --capability <booking-calendly|multilingual> --approved-plan sha256:<digest>` accepts no capability settings. Builder-core recomputes the exact accepted subject-specific removal plan and fingerprint in the same clean, stable, attached linked worktree, executes one ownership-aware batch that can delete, replace, preserve, and eject only planned surfaces, verifies a separate copy, re-infers before persistence, and completes migration append followed by state-last persistence. It then requires exact final desired/installed/inferred agreement, exact control-file bytes, preservation of modified or already-ejected application-owned surfaces, and the exact final Git diff before returning `verified-final-diff-approval-required`; that result is evidence awaiting verified-final-diff approval. A repeat removal returns exact `CAPABILITY_NOT_INSTALLED` without mutation. Failures before a write require no recovery; failures after a write retain the isolated-worktree prefix for inspection rather than rolling it back automatically.

`apply-upgrade --directory <absolute-existing-linked-worktree> --capability standards --to-version 0.4.0 --approved-plan sha256:<digest>` has exactly those four arguments and accepts no `--from-version`. It consumes only the exact approved `plan-upgrade` fingerprint for the single `standards@0.3.0` to `standards@0.4.0` edge. Builder-core recomputes the complete plan and stable Git identity immediately before its upgrade-specific six-action write, transforms once, runs ordinary verification, freshly infers, appends migration `upgrade-standards-0-3-0-to-0-4-0`, persists state last, proves final state/inference/migration agreement and the exact eight-path diff, and returns `verified-final-diff-approval-required`. Planning approval, execution, verification, persistence, recovery, and verified-final-diff approval remain separate. A failure after a committed write retains its inspectable prefix and never triggers automatic rollback.

For exact `site-routing@0.3.0` to `0.4.0`, `apply-upgrade` consumes the corresponding approved fingerprint, applies the exact 22-action production-site batch, verifies and re-infers, appends migration `upgrade-site-routing-0-3-0-to-0-4-0`, persists `site@0.11.0` state last, and stops at the same verified-final-diff boundary. It does not certify the pending successor subject.

`plan-profile-transition --directory <absolute-existing-linked-worktree> --to-profile site` plans only exact `portfolio@0.10.0` to `site@0.10.0`, infers the source with no `--from-profile`, and returns the seven exact ownership-aware actions without executing them. It requires a clean attached linked worktree before and after planning, rejects present and ignored create targets plus hidden index state, and preserves every repository byte. Success is approval-required; refusal uses stable recovery `not-required`. The output excludes private repository paths/metadata, project content/settings, credentials, and personal data.

`apply-profile-transition --directory <absolute-existing-linked-worktree> --to-profile site --approved-plan sha256:<digest>` accepts exactly those three arguments and no `--from-profile`. It consumes only the exact accepted planner fingerprint. Builder-core recomputes the plan and Git identity, writes the seven actions once through its transition-specific writer, verifies an isolated copy without VCS metadata, freshly infers, appends migration `transition-portfolio-0-10-0-to-site-0-10-0`, persists state last with a `profile-transition` receipt, and proves final agreement plus the exact nine-path diff before returning `verified-final-diff-approval-required`. Optional Calendly selection/settings remain unchanged. Failures before a committed write use `not-required`; later failures retain the inspectable worktree prefix with `inspect-worktree` and never roll back automatically.

The CLI has no prompt, overwrite mode, generic existing-repository mutation, third upgrade or second profile-transition edge, lifecycle extraction, deployment, publication, Calendly account configuration, provider API, provider-data ownership, credential handling, or persistent-data cleanup behavior. Local creation, inspection, planning, and the exact Calendly, multilingual, standards, site-routing, and portfolio-to-site transactions do not establish final-diff approval, automated recovery, lifecycle certification, translation quality, deployed behavior, provider behavior, performance or visual quality, security clearance, production readiness, human accessibility, or WCAG conformance.

The canonical API and lifecycle owner is [package ownership](../../docs/architecture/package-ownership.md).
