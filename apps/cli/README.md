# `@egeria-systems/cli`

Private command adapter for the Egeria Systems builder kernel.

The approved boundary contains ten exact commands: `create`, `infer`, `doctor`, `diff`, `plan-add`, `apply-add`, `plan-remove`, `apply-remove`, `plan-profile-transition`, and `apply-profile-transition`. Planning is read-only; every apply command is fingerprint-gated. The adapter delegates builder policy and emits one content-safe JSON line with stable exits.

New creation selects `portfolio@0.12.0`, `site@0.13.0`, or `app@0.3.0` under [ADR-0020](../../docs/adr/0020-application-environments.md). The default app composes `app-foundation@0.3.0 + site-routing@0.5.0`, retaining the complete production-site experience from [ADR-0013](../../docs/adr/0013-convergent-app-profile.md). Direct `effect@4.0.0-rc.112` belongs only to generated server modules under [ADR-0014](../../docs/adr/0014-selective-effect-application-runtime.md); the CLI remains Effect-free. The [app lifecycle summary](../../README.md#app-lifecycle-and-verification) lists current edges and retired operations, optional-subset coverage, unsupported operations, and separate recovery domains. The [enforcement map](../../docs/architecture/enforcement-map.md) names verification owners, and the [lifecycle protocol](../../docs/governance/review-and-contribution.md) owns approval gates. Current certification follows the [capability model](../../docs/architecture/capability-model.md#certification-coverage); invoking the CLI does not certify a subject. Project and installed-state controls use schema `2.0.0`; the [application environment boundary](../../docs/architecture/capability-model.md#application-environments) owns current recipes, settings and lifecycle admission. This source candidate still requires runtime, visual and certification acceptance.

`create` generates only a previously absent portfolio, site, or app directory through the verified state-last builder-core boundary. It accepts the exact base creation arguments, independent flags `--multilingual`, `--transactional-email-resend`, `--background-job-delivery` and `--contact-form-web3forms`. Only app accepts `--application-persistence`. All three profiles accept the paired `--booking-calendly` and `--calendly-mode` selection-only options. Valid modes are `link`, `inline` and `popup`. The strict analytics options cover Cloudflare Web Analytics, Google Analytics 4, Microsoft Clarity, Google Search Console and Looker Studio. Analytics requires at least one runtime provider or Search Console; Looker Studio requires GA4; and Clarity requires `--microsoft-clarity-audience not-directed-to-minors`. Builder-core owns selected-capability/settings agreement and sanitized validation issues. CLI output never returns provider identifiers. Analytics selects providers with `--cloudflare-web-analytics`, `--google-analytics-4`, `--microsoft-clarity`, `--google-search-console`, and `--looker-studio`. Literal provider destinations, tokens and IDs are rejected. Build inputs and runtime secrets are supplied through the generated application environment contract.

`infer`, `doctor`, and `diff` are read-only and evaluate declared Calendly, multilingual, analytics, application-persistence, transactional-email, and background-job-delivery settings/surfaces through builder-core when installed. `plan-add` is also read-only: for a clean attached linked worktree, it checks current project health and returns a deterministic, redacted approval-required plan for adding exact `booking-calendly@0.2.0` with mode-only settings, `multilingual@0.1.0` without settings, `analytics@0.2.0` with provider selections, app-only `application-persistence@0.2.0`, `transactional-email-resend@0.2.0`, or `contact-form-web3forms@0.2.0`. Jobs-bearing sources and jobs addition are unsupported. It detects tracked changes, all non-ignored untracked files, and the `assume-unchanged` and `skip-worktree` index flags. It requires exact canonical managed-surface inventory and installed application-owned paths to remain files without comparing their content fingerprints. It refuses managed drift, ejections, present collisions, absent but ignored create targets, operations, conflicts, detached or primary worktrees, unexpected Git/reader failures, and a changed final Git identity. It never creates the worktree or branch and performs no transform, migration, state update, dependency installation, provider action, or identifier disclosure.

`plan-remove` is also read-only and supports the same six exact optional capabilities in current environment recipes; persistence remains app-only. Jobs-bearing sources and jobs removal are unsupported. Persistence planning requires `--persistence-removal <absolute-json-path>` and returns the machine review report with the source-removal plan. Between two matching clean linked-worktree inspections, builder-core requires exact desired, installed, inferred, inventory, and ejection agreement; refuses managed or shared-composition drift; and returns path-sorted actions that delete unchanged capability files, replace shared composition and project configuration, or preserve modified/already-ejected application files as `preserve-file-and-eject`. Every plan contains a fingerprint-bound repository-wide surviving-reference review requirement; analytics additionally requires explicit provider-account, retained-data, browser-storage, and cookie disposition review. The public plan redacts settings and Git metadata except for the intentional base revision while its fingerprint binds the full private project, state, actions, review requirements, and Git identity. A clean repository without the requested capability returns exact `CAPABILITY_NOT_INSTALLED`. Planning performs no deletion, replacement, ejection, verification, migration append, state write, dependency change, provider cleanup, or provider action.

Optional `application-persistence@0.2.0` also uses `plan-add`/`apply-add` and `plan-remove`/`apply-remove` for the exact app tuple. Its removal requires bounded evidence input, a machine review report produced by planning, and human review of the exact report and plan. The [persistence boundary](../../docs/architecture/capability-model.md#application-persistence-boundary) owns supported inputs, preservation, verification and separate provider/data recovery gates.

Optional transactional email preserves profile identity, adds its required foundation, and retains foundation after email removal. The CLI accepts no email addresses or credentials; runtime configuration and provider/key/retention dispositions remain separate. The [email boundary](../../docs/architecture/capability-model.md#transactional-email-boundary) owns exact supported tuples, verification and reviewed source-removal limits.

`plan-upgrade` and `apply-upgrade` are absent and fail argument parsing before adapter access. Historical standards and site-routing upgrades and portfolio-to-site transitions are retired from the current executable surface; prior acceptance remains historical under [ADR-0015](../../docs/adr/0015-vitest-five-generation.md) and the [capability model](../../docs/architecture/capability-model.md#application-environments).

`apply-add` accepts the same six optional selections and their allowed settings, plus the exact `sha256:` plan fingerprint. Builder-core recomputes that subject-specific plan in the same clean linked worktree, writes only its planned actions, verifies a separate copy, re-infers, appends one successful migration record, writes state last, re-infers again, and requires the exact expected dirty paths. Success stops at `verified-final-diff-approval-required`. Failures return only a stable phase and either `not-required` or `inspect-worktree` recovery; the CLI never resets, cleans, commits, creates the worktree or branch, contacts a provider, or rolls a partial prefix back automatically.

`apply-remove --directory <absolute-existing-linked-worktree> --capability <analytics|application-persistence|booking-calendly|contact-form-web3forms|multilingual|transactional-email-resend> --approved-plan sha256:<digest>` accepts no capability settings. Application persistence is restricted to the supported app tuple and additionally requires `--persistence-removal <absolute-json-path>` and `--persistence-human-review <absolute-json-path>` for bounded evidence and human dispositions of the exact machine report; `--approved-plan` binds the reviewed source-removal plan. Builder-core recomputes the exact accepted subject-specific removal plan and fingerprint in the same clean, stable, attached linked worktree, executes one ownership-aware batch that can delete, replace, preserve, and eject only planned surfaces, verifies a separate copy, re-infers before persistence, and completes migration append followed by state-last persistence. It then requires exact final desired/installed/inferred agreement, exact control-file bytes, preservation of modified or already-ejected application-owned surfaces, and the exact final Git diff before returning `verified-final-diff-approval-required`; that result is evidence awaiting verified-final-diff approval. A repeat removal returns exact `CAPABILITY_NOT_INSTALLED` without mutation. Analytics source removal does not delete provider accounts, retained provider data, browser data outside the generated cleanup contract, or any external resource. Failures before a write require no recovery; failures after a write retain the isolated-worktree prefix for inspection rather than rolling it back automatically.

`plan-profile-transition --directory <absolute-existing-linked-worktree> --to-profile app` accepts no `--from-profile`. Builder-core owns exactly `portfolio@0.12.0` and `site@0.13.0` to `app@0.3.0`, covering the eight booking/multilingual/analytics subsets. Contact, email or retained foundation, persistence and jobs sources refuse. Portfolio transition remains closed until the exact environment visual assets are accepted; site transitions preserve customized UI and locale content. Planning infers the source and returns the exact ownership-aware actions without executing them. It requires a clean attached linked worktree before and after planning, rejects present and ignored create targets plus hidden index state, and preserves every repository byte. Success is approval-required; refusal uses stable recovery `not-required`. The output excludes private repository paths/metadata, project content/settings, credentials, and personal data.

`apply-profile-transition --directory <absolute-existing-linked-worktree> --to-profile app --approved-plan sha256:<digest>` accepts exactly those three arguments and no `--from-profile`. It consumes only the exact accepted planner fingerprint for the same declared edges. Builder-core owns all transformation, verification, inference, persistence, final-diff, and recovery policy. The [incoming app execution boundary](../../docs/architecture/capability-model.md#incoming-app-transition-execution) owns app content/settings preservation, whole-Worker verification, project/migration/state ordering, and exact dynamic final-diff checks. Every success returns `verified-final-diff-approval-required`. Failures before a committed write use `not-required`; later failures retain the inspectable worktree prefix with `inspect-worktree` and never roll back automatically.

The CLI has no prompt, overwrite mode, generic existing-repository mutation, undeclared upgrade or profile-transition edge, lifecycle extraction, deployment, publication, Calendly or analytics account configuration, provider API, provider-data ownership, credential handling, or persistent-data cleanup behavior. Local creation, inspection, planning, and the six optional-capability and incoming app transactions do not establish final-diff approval, automated recovery, lifecycle certification, translation quality, deployed behavior, provider behavior, privacy or legal compliance, performance or visual quality, security clearance, production readiness, human accessibility, or WCAG conformance.

The canonical API and lifecycle owner is [package ownership](../../docs/architecture/package-ownership.md).

Optional `create --background-job-delivery` selects jobs `0.3.0` on current portfolio, site and app recipes independently of persistence and email. Jobs source lifecycle is unsupported in the current environment contract, including operations on jobs-bearing projects. The [jobs boundary](../../docs/architecture/capability-model.md#background-job-delivery-boundary) retains historical evidence and separate operator limits.
