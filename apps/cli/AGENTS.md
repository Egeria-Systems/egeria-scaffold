# Builder CLI boundary

Unused public generations, capability-upgrade commands and old profile-transition edges are retired under [ADR-0020](../../docs/adr/0020-application-environments.md#early-retirement-of-unused-public-generations). Historical evidence remains preserved; unsupported controls refuse before effects. [ADR-0015](../../docs/adr/0015-vitest-five-generation.md#patched-public-generation) owns the exact current dependency and recipe tuples.

The [application environment boundary](../../docs/architecture/capability-model.md#application-environments) qualifies only the related target/settings and unused-generation preservation rules below. Assemble the finite candidate internally; public CLI/defaults change only with its complete consumers. Selection-only inputs and unknown/obsolete/mixed installed-state refusal must precede writes; preserve operation-specific safeguards and the exact jobs lifecycle/refusal boundary. [ADR-0020](../../docs/adr/0020-application-environments.md#generation-and-precise-supersessions) owns the precise retirement boundary. Routine stream approval uses only the [scoped governance exception](../../docs/governance/review-and-contribution.md#lean-application-environments-delivery-exception).

The [common configuration internal candidate](../../docs/architecture/capability-model.md#common-configuration-internal-candidate) owns the implemented explicit parser/runner mode and its create/infer/doctor limits; the [booking candidate](../../docs/architecture/capability-model.md#booking-internal-candidate) owns mode-only booking and composed contact lifecycle. `productionRunner` remains on public defaults; no shipped command or environment switch activates the candidate. The [analytics candidate](../../docs/architecture/capability-model.md#analytics-internal-candidate) owns selection-only analytics admission, compiled configuration, consent context and exact neighbor-preserving lifecycle.

Read the repository [`AGENTS.md`](../../AGENTS.md), the canonical [package ownership](../../docs/architecture/package-ownership.md), and the [review and contribution protocol](../../docs/governance/review-and-contribution.md) before editing this surface.

`apps/cli` is the private executable adapter for the builder kernel.

- The approved boundary contains ten exact commands: `create`, `infer`, `doctor`, `diff`, `plan-add`, `apply-add`, `plan-remove`, `apply-remove`, `plan-profile-transition`, and `apply-profile-transition`. Planning is read-only; every apply command is fingerprint-gated. The adapter delegates builder policy and emits one content-safe JSON line with stable exits.
- Keep command input/output thin. Builder decisions, repository transformations, schemas, profile recipes, state, inference, and diagnostics belong to `packages/builder-core`.
- Builder-core's shared profile/state contracts admit `portfolio`, `site`, and `app`; CLI `create` uses that shared identifier and delegates new-directory generation without profile-specific policy. Keep Effect out of the CLI. The existing profile-transition commands accept only `site` or `app` targets and delegate the exact declared edges to builder-core. Add no command, setting, dependency handling, or runtime interpretation. The [capability model](../../docs/architecture/capability-model.md#accepted-app-architecture-boundary) owns app lifecycle availability and remaining gates.
- `create` may call only builder-core's approved new-directory generation boundary. It accepts exact optional Calendly settings, strict optional analytics provider and operational-integration settings, and the independent boolean `--multilingual` app-only `--application-persistence`, current-profile `--transactional-email-resend` and `--background-job-delivery`, and strict public `--web3forms-access-key` selections; it accepts no caller-supplied generic capability list. It does not add overwrite, interactive prompt, Git, deployment, publication, provider action, external property/connector configuration, or existing-repository mutation behavior.
- `infer`, `doctor`, and `diff` remain read-only and must not install dependencies or change repository bytes. Delegate retained-generation selection to builder-core; preserve supported installed diagnostics and refuse retired controls under [ADR-0015](../../docs/adr/0015-vitest-five-generation.md).
- `plan-add` remains read-only and is limited to the closed subjects `analytics@0.1.0` with strict validated analytics settings, `booking-calendly@0.1.0` with paired validated Calendly settings, and `multilingual@0.1.0` or `application-persistence@0.1.1` or `transactional-email-resend@0.1.0` with no settings, or `contact-form-web3forms@0.1.0` with its strict public access key, plus exact jobs under the [jobs boundary](../../docs/architecture/capability-model.md#exact-jobs-lifecycle). Require builder-core's clean attached linked worktree preflight before and after planning, exact canonical managed-surface inventory, application-owned surface availability, rejection of hidden tracked state and ignored create targets, and containment of unexpected reader/Git failures under their stable codes. Return only the redacted plan or refusal code, and never create the worktree or branch. Do not transform, migrate, persist state, install dependencies, contact a provider, or configure an external property/connector.
- `apply-add` is limited to the exact approved `analytics@0.1.0`, `booking-calendly@0.1.0`, `multilingual@0.1.0`, or `application-persistence@0.1.1` or `transactional-email-resend@0.1.0` or `contact-form-web3forms@0.1.0` plan fingerprint, plus exact jobs under the [jobs boundary](../../docs/architecture/capability-model.md#exact-jobs-lifecycle) in the same clean attached linked worktree. Delegate subject-specific transformation, isolated generated-project verification, re-inference, migration append, state-last persistence, post-state agreement, exact dirty-path inspection, and recovery classification to builder-core. Emit only the bounded result or refusal/recovery envelope. Never create the branch/worktree, commit, reset, clean, deploy, publish, contact a provider, configure an external property/connector, or treat successful execution as verified-final-diff approval.
- `plan-remove` remains read-only and is limited to exact installed and desired `analytics@0.1.0`, `booking-calendly@0.1.0`, `multilingual@0.1.0`, or `application-persistence@0.1.1` or `transactional-email-resend@0.1.0` or `contact-form-web3forms@0.1.0`, plus exact jobs under the [jobs boundary](../../docs/architecture/capability-model.md#exact-jobs-lifecycle). Require the same clean attached linked-worktree preflight before and after planning, exact desired/installed/inferred agreement, canonical surface inventory, exact managed and shared-composition bytes, and consistent ejection metadata. Classify unchanged capability-owned files for deletion and modified capability-owned application-owned files for preservation and ejection without changing them. Return only the redacted approval plan or stable refusal, and never delete, transform, verify, migrate, persist state, install dependencies, create a branch/worktree, contact a provider, or dispose of credentials, browser data, or external data.
- `apply-remove` is the exact current removal command and is limited to consuming the exact `plan-remove` fingerprint for `analytics@0.1.0`, `booking-calendly@0.1.0`, `multilingual@0.1.0`, or `application-persistence@0.1.1` or `transactional-email-resend@0.1.0` or `contact-form-web3forms@0.1.0`, plus exact jobs under the [jobs boundary](../../docs/architecture/capability-model.md#exact-jobs-lifecycle), in that same eligible linked worktree. Delegate ownership-aware deletion, replacement, preservation/ejection, isolated verification, re-inference, migration append, state-last persistence, exact final agreement, and exact final Git-diff inspection to builder-core. It may add no settings, generic transformation, provider action, credential/browser/external-data disposition, persistent-data cleanup, or automatic rollback behavior, and success remains subject to separate verified-final-diff approval.
- `plan-profile-transition` remains read-only and accepts exactly `--directory` and `--to-profile <site|app>`, with no `--from-profile`. Delegate the exact supported edges and their action inventories to builder-core under the [capability model](../../docs/architecture/capability-model.md#accepted-app-architecture-boundary). Require the same clean stable attached linked-worktree preflight before and after planning, reject present and ignored create targets, and delegate source inference, transition support, desired/installed/inferred/project/state/migration/recipe/capability/surface agreement, exact private fingerprint material, and stable refusal. Emit one privacy-safe plan or refusal with recovery `not-required`. Never transform, verify transformed behavior, migrate, persist state, execute a transition, create a branch/worktree, install dependencies, or contact a provider.
- `apply-profile-transition` accepts exactly `--directory`, `--to-profile <site|app>`, and `--approved-plan` for the same exact declared edges. It accepts no `--from-profile` or caller-supplied capabilities/settings. Delegate exact plan/Git recomputation, operation-specific writes, isolated verification, fresh inference, migration, state-last persistence with receipt kind `profile-transition`, final agreement, and exact-diff inspection to builder-core. The [capability model](../../docs/architecture/capability-model.md#incoming-app-transition-execution) owns incoming app ordering, Worker receipts, preserved inputs, and recovery; historical portfolio-to-site execution is retired. A failure after a committed write retains its inspectable prefix and never triggers automatic rollback. Success stops at `verified-final-diff-approval-required` and does not supply separate final-diff approval.
- Test this adapter with Node's test runner (`node --test`) through `pnpm run test:cli`. Cover argument parsing and process/output contracts with focused unit and subprocess tests. The compiled `plan-profile-transition` integrations use representative temporary linked worktrees and exact no-mutation assertions. The compiled `apply-add`, `apply-remove`, exact `apply-profile-transition` integrations execute builder-core's isolated generated-project verifier; multilingual and analytics journeys cover the portfolio/site profiles and their independent installation order. The compiled current incoming app journeys additionally execute the built-Worker health integration under the [app verification boundary](../../docs/architecture/capability-model.md#accepted-app-architecture-boundary). Parser and injected-adapter tests do not establish generated runtime results. No CLI test proves browser behavior, deployment, provider behavior, linguistic quality, visual quality, accessibility conformance, lifecycle certification, legal compliance, or production readiness.
- Exact `multilingual@0.1.0` is certified only from the separate accepted `fresh-scaffold` and `existing-repository-lifecycle` receipt at evidence revision `96b587a254cf6fc859867d6fc66c7e0c900c4cfd`; analytics certification is outside this implementation increment. No create, plan, apply, test, or local build result may independently be represented as certification.
- Do not expose this application as a public package.
- Follow the currently approved increment and stop at its review gate before expanding this boundary.

Preserve exact supported installed tuples and inert historical evidence. Keep machine evidence assessment in builder-core; the CLI reads only bounded strict input and human-review envelopes. Source removal does not authorize persistent-data or provider operations.

Source-only removal does not revoke credentials or change provider state.

Preserve independent Resend behavior and installed foundation/persistence verification. No live provider certification or external data disposition is implied by local implementation.

Optional jobs generation, exact source lifecycle and bounded operator tooling follow the [background job delivery boundary](../../docs/architecture/capability-model.md#background-job-delivery-boundary). Preserve exact default/installed views and the closed lifecycle allowlist; no provider, replay, drain or deployment authority is implied.
