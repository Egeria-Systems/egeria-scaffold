# Builder CLI boundary

The [current environment generation](../../docs/architecture/capability-model.md#current-environment-generation) owns the schema-2 public source candidate, exact installed tuples, current lifecycle and pending acceptance. [ADR-0020](../../docs/adr/0020-application-environments.md#public-environment-generation-activation) owns the precise retirement of old executable generation and edges. Preserve its operation-specific safeguards, historical evidence and separate runtime/certification/publication gates. Routine stream approval uses only the [scoped governance exception](../../docs/governance/review-and-contribution.md#lean-application-environments-delivery-exception).

Read the repository [`AGENTS.md`](../../AGENTS.md), the canonical [package ownership](../../docs/architecture/package-ownership.md), and the [review and contribution protocol](../../docs/governance/review-and-contribution.md) before editing this surface.

`apps/cli` is the private executable adapter for the builder kernel.

- The approved boundary contains ten exact commands: `create`, `infer`, `doctor`, `diff`, `plan-add`, `apply-add`, `plan-remove`, `apply-remove`, `plan-profile-transition`, and `apply-profile-transition`. Planning is read-only; every apply command is fingerprint-gated. The adapter delegates builder policy and emits one content-safe JSON line with stable exits.
- Keep command input/output thin. Builder decisions, repository transformations, schemas, profile recipes, state, inference, and diagnostics belong to `packages/builder-core`.
- Builder-core's shared profile/state contracts admit `portfolio`, `site`, and `app`; CLI `create` uses that shared identifier and delegates new-directory generation without profile-specific policy. Keep Effect out of the CLI. The existing profile-transition commands accept only `site` or `app` targets and delegate the exact declared edges to builder-core. Add no command, setting, dependency handling, or runtime interpretation. The [capability model](../../docs/architecture/capability-model.md#accepted-app-architecture-boundary) owns app lifecycle availability and remaining gates.
- `create` delegates only to the approved new-directory generator. It accepts selection-only contact, booking mode, analytics providers/audience/operational integrations, multilingual, app-only persistence, transactional email and jobs. Literal destination flags refuse before adapter access. Add no generic capability list, overwrite, Git mutation, deployment, publication or provider behavior.
- `infer`, `doctor`, and `diff` remain read-only and never install dependencies or change bytes. Derive the exact current installed tuple in builder-core; unknown, retired, missing or mixed controls remain invalid and never fall back to generation defaults.
- `plan-add` remains read-only and is limited to the closed subjects `analytics@0.2.0` with validated selection-only analytics settings, `booking-calendly@0.2.0` with mode-only Calendly settings, and `multilingual@0.1.1` or `application-persistence@0.2.0` or `transactional-email-resend@0.2.0` with no settings, or `contact-form-web3forms@0.2.0` with no stored destination setting, with jobs-bearing source and desired jobs lifecycle operations refused. Require builder-core's clean attached linked worktree preflight before and after planning, exact canonical managed-surface inventory, application-owned surface availability, rejection of hidden tracked state and ignored create targets, and containment of unexpected reader/Git failures under their stable codes. Return only the redacted plan or refusal code, and never create the worktree or branch. Do not transform, migrate, persist state, install dependencies, contact a provider, or configure an external property/connector.
- `apply-add` is limited to the exact approved `analytics@0.2.0`, `booking-calendly@0.2.0`, `multilingual@0.1.1`, or `application-persistence@0.2.0` or `transactional-email-resend@0.2.0` or `contact-form-web3forms@0.2.0` plan fingerprint, with jobs-bearing source and desired jobs lifecycle operations refused in the same clean attached linked worktree. Delegate subject-specific transformation, isolated generated-project verification, re-inference, migration append, state-last persistence, post-state agreement, exact dirty-path inspection, and recovery classification to builder-core. Emit only the bounded result or refusal/recovery envelope. Never create the branch/worktree, commit, reset, clean, deploy, publish, contact a provider, configure an external property/connector, or treat successful execution as verified-final-diff approval.
- `plan-remove` remains read-only and is limited to exact installed and desired `analytics@0.2.0`, `booking-calendly@0.2.0`, `multilingual@0.1.1`, or `application-persistence@0.2.0` or `transactional-email-resend@0.2.0` or `contact-form-web3forms@0.2.0`, with jobs-bearing source and desired jobs lifecycle operations refused. Require the same clean attached linked-worktree preflight before and after planning, exact desired/installed/inferred agreement, canonical surface inventory, exact managed and shared-composition bytes, and consistent ejection metadata. Classify unchanged capability-owned files for deletion and modified capability-owned application-owned files for preservation and ejection without changing them. Return only the redacted approval plan or stable refusal, and never delete, transform, verify, migrate, persist state, install dependencies, create a branch/worktree, contact a provider, or dispose of credentials, browser data, or external data.
- `apply-remove` is the exact current removal command and is limited to consuming the exact `plan-remove` fingerprint for `analytics@0.2.0`, `booking-calendly@0.2.0`, `multilingual@0.1.1`, or `application-persistence@0.2.0` or `transactional-email-resend@0.2.0` or `contact-form-web3forms@0.2.0`, with jobs-bearing source and desired jobs lifecycle operations refused, in that same eligible linked worktree. Delegate ownership-aware deletion, replacement, preservation/ejection, isolated verification, re-inference, migration append, state-last persistence, exact final agreement, and exact final Git-diff inspection to builder-core. It may add no settings, generic transformation, provider action, credential/browser/external-data disposition, persistent-data cleanup, or automatic rollback behavior, and success remains subject to separate verified-final-diff approval.
- Retired upgrade commands and APIs are absent. Do not restore their parser routes, executors or migration edges.

- `plan-profile-transition` remains read-only and accepts exactly `--directory` and `--to-profile <site|app>`, with no `--from-profile`. Delegate the exact supported edges and their action inventories to builder-core under the [capability model](../../docs/architecture/capability-model.md#accepted-app-architecture-boundary). Require the same clean stable attached linked-worktree preflight before and after planning, reject present and ignored create targets, and delegate source inference, transition support, desired/installed/inferred/project/state/migration/recipe/capability/surface agreement, exact private fingerprint material, and stable refusal. Emit one privacy-safe plan or refusal with recovery `not-required`. Never transform, verify transformed behavior, migrate, persist state, execute a transition, create a branch/worktree, install dependencies, or contact a provider.
- `apply-profile-transition` accepts exactly `--directory`, `--to-profile <site|app>`, and `--approved-plan` for the same exact declared edges. It accepts no `--from-profile` or caller-supplied capabilities/settings. Delegate exact plan/Git recomputation, operation-specific writes, isolated verification, fresh inference, migration, state-last persistence with receipt kind `profile-transition`, final agreement, and exact-diff inspection to builder-core. The [capability model](../../docs/architecture/capability-model.md#incoming-app-transition-execution) owns incoming app ordering, Worker receipts, preserved inputs, and recovery; portfolio-to-site returns unsupported without mutation. A failure after a committed write retains its inspectable prefix and never triggers automatic rollback. Success stops at `verified-final-diff-approval-required` and does not supply separate final-diff approval.
- Test parsing and adapter boundaries with Node (`node --test`), and actual current lifecycle with compiled CLI subprocess journeys only after their execution method and generated runtime are admitted. `pnpm run test:cli` is the complete CLI aggregate and requires that broader admission. Mixed tests that include a real verifier remain runtime tests even if other branches use injected adapters. Preserve production verifier branches and failure-prefix assertions; passing parser tests do not prove generated behavior, certification or release readiness.
- Historical multilingual and provider receipts retain their exact identities. All current certification renewal follows the canonical boundary; no command, test or build result independently certifies a capability.
- Do not expose this application as a public package.
- Follow the currently approved increment and stop at its review gate before expanding this boundary.

Optional application persistence follows [ADR-0016](../../docs/adr/0016-optional-application-persistence.md) and the [capability model](../../docs/architecture/capability-model.md#application-persistence-boundary). Select the exact current installed tuple; refuse retired or mixed controls. Keep machine evidence assessment in builder-core; the CLI reads only bounded strict input and human-review envelopes. Source removal does not authorize persistent-data or provider operations.

Optional transactional email follows [ADR-0017](../../docs/adr/0017-transactional-email-resend.md) and the [email boundary](../../docs/architecture/capability-model.md#transactional-email-boundary). Current portfolio/site email selection adds foundation without changing profile; removal retains foundation. Exact installed foundation controls Worker verification. Source-only removal does not revoke credentials or change provider state.

Optional hosted contact follows [ADR-0018](../../docs/adr/0018-hosted-contact-form.md) and the [contact boundary](../../docs/architecture/capability-model.md#hosted-contact-form-boundary). Preserve independent Resend behavior and installed foundation/persistence verification. No live provider certification or external data disposition is implied by local implementation.

Optional jobs generation and retained operator contracts follow the [background job delivery boundary](../../docs/architecture/capability-model.md#background-job-delivery-boundary). Preserve exact current installed views and the jobs lifecycle refusal; no provider, replay, drain or deployment authority is implied.
