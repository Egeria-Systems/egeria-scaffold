## Supported upgrade planning boundary

`egeria plan-upgrade --directory <absolute-existing-linked-worktree> --capability standards --to-version 0.4.0` is read-only. It infers exact installed `standards@0.3.0`; validates recipe `0.9.0` provenance and desired, installed, inferred, project, state, migration, and surface-inventory agreement; and returns six ownership-aware target actions plus exact control/target fingerprints. Clean stable attached isolated-worktree checks run before and after planning, including rejection of ignored create targets. The command emits one privacy-safe JSON line and leaves `project.yaml`, `state.json`, `migrations.jsonl`, and every repository byte unchanged on success or refusal.

Only this pre-`1.0.0` edge is declared. `standards@0.4.0` is already current; other source versions have no edge; ambiguous inference, incompatible state, drift, ejection, collisions, and unsafe Git state refuse planning. The command has no `--from-version` and does not execute, verify, migrate, persist, roll back, or approve an upgrade. Portfolio-to-site remains a later independent profile transition.

`egeria apply-upgrade --directory <absolute-existing-linked-worktree> --capability standards --to-version 0.4.0 --approved-plan sha256:<digest>` accepts exactly those four arguments and no caller-supplied source version. It consumes only the approved plan fingerprint for `standards@0.3.0` to `standards@0.4.0`, revalidates the complete plan and Git identity before the upgrade-specific six-action write, transforms once, runs ordinary verification, freshly infers, appends the exact successful migration, persists state last, and proves final agreement and the exact eight-path diff. Original recipe provenance remains `0.9.0`; project/state/migration schema remains `1.0.0`; builder remains `0.0.0`. Failures after a committed write retain an inspectable prefix and never trigger automatic rollback. Success stops at `verified-final-diff-approval-required`: planning approval, execution, verification, persistence, recovery, and verified-final-diff approval remain separate.

Acceptance does not certify, deploy, publish, establish browser/workerd or provider behavior, prove visual quality or accessibility conformance, establish security certification or production readiness, or provide a generated-project final-diff approval.

## Supported profile-transition planning boundary

`egeria plan-profile-transition --directory <absolute-existing-linked-worktree> --to-profile site` is completely read-only and supports only exact `portfolio@0.10.0` to `site@0.10.0`. It infers the source profile from exact project/state/migration/recipe/capability/inference/surface agreement and accepts no `--from-profile`. Builder-core owns the transition edge, seven render-derived actions, fingerprint, refusal, privacy, and no-mutation policy; the CLI is a thin Git/filesystem and one-line JSON adapter.

Success emits one approval-required JSON plan on stdout with exit `0`. Planning refusal emits one privacy-safe JSON error on stderr with exit `1`; malformed command arguments emit `CLI_ARGUMENT_INVALID` on stderr with exit `2`. Refusals use recovery `not-required`. The command requires a clean stable attached isolated linked worktree before and after planning, rejects hidden index state and present or ignored create targets, and leaves `.egeria/project.yaml`, `.egeria/state.json`, `.egeria/migrations.jsonl`, managed surfaces, Git metadata, and every repository byte unchanged. It does not execute, verify transformed behavior, migrate, persist state, create a branch/worktree, commit, reset, clean, deploy, publish, certify, or contact a provider.

`egeria apply-profile-transition --directory <absolute-existing-linked-worktree> --to-profile site --approved-plan sha256:<digest>` consumes only that exact accepted fingerprint. Builder-core recomputes the plan and Git identity, uses its operation-specific writer to apply the seven actions once, verifies a VCS-free isolated copy, freshly infers, appends migration `transition-portfolio-0-10-0-to-site-0-10-0`, persists state last with a `profile-transition` receipt, and proves final agreement plus the exact nine-path diff before returning `verified-final-diff-approval-required`. Optional Calendly selection/settings remain unchanged. Failures before a committed write require no recovery; later failures retain the inspectable worktree prefix without automatic rollback. The command creates no branch/worktree, commit, provider action, deployment, publication, certification, or final-diff approval.

## Calendly scaffold boundary

Calendly is an explicit optional selection for initial `portfolio` or `site` creation; it is not a recipe default. A clean attached linked worktree can receive a redacted approval-required plan and apply that exact fingerprint through the bounded addition transaction. The paired CLI options accept `link`, `inline`, or `popup` plus a bounded HTTPS destination on `calendly.com` or `www.calendly.com` with no query string. Selection and strict settings are recorded together in `.egeria/project.yaml`; the installed capability and managed-surface fingerprints are recorded in `.egeria/state.json` and checked by inference.

`plan-add` treats tracked changes, all non-ignored untracked files, and the `assume-unchanged` and `skip-worktree` index flags as dirty. It requires the installed state to retain the exact canonical managed-surface inventory and installed application-owned paths to remain files, while ignoring application-owned content fingerprints. It refuses managed drift, ejections, present or ignored create-target collisions, Git operations/conflicts, primary or detached worktrees, unexpected Git/reader failures, and identity changes between its two inspections. It redacts settings and branch/root/Git-directory/dirty-path metadata while intentionally retaining the exact base revision. Its deterministic fingerprint binds the full private plan input and exact Git identity.

`plan-remove` is read-only for exact installed `booking-calendly@0.1.0` in current `portfolio` and `site` recipes. It requires exact control, desired/installed/inferred, inventory, and ejection agreement; refuses managed and shared-route drift; classifies unchanged capability files for deletion and modified/already-ejected application files for `preserve-file-and-eject`; and returns exact `CAPABILITY_NOT_INSTALLED` for a clean repository without the capability. Every approval plan requires a repository-wide review for surviving references to removed surfaces, and a plan with preserved/ejected capability files additionally names their exact paths for reconciliation before transformation approval. These fingerprint-bound requirements do not claim that the current planner scans arbitrary repository source. Its path-sorted public plan is redacted while the fingerprint binds the full private project, installed state, actions, review requirements, and Git identity. It does not execute any action or persist state.

`apply-remove` is the exact current removal command. It recomputes that exact plan and accepts only its fingerprint in the same clean, stable, attached linked worktree. It executes the ownership-aware delete/replace/preserve/eject batch once, verifies an isolated copy and re-infers before persistence, appends the removal migration, writes state last, and then requires exact desired/installed/inferred agreement, exact control bytes, preserved/ejected surfaces, and the exact final Git diff. Repeat removal returns `CAPABILITY_NOT_INSTALLED` without mutation. Success stops at `verified-final-diff-approval-required`; no lifecycle command creates the branch/worktree, commits, resets, cleans, contacts a provider, or automatically rolls a failure prefix back.

`apply-add` recomputes its addition plan in the same clean linked worktree and accepts only the exact fingerprint. It writes seven planned Calendly source/configuration actions, verifies an isolated copy, re-infers, appends one migration record, persists state last, verifies final agreement, and requires the exact expected dirty paths. Its result is local transaction evidence awaiting verified-final-diff approval, not automated recovery, certification, deployment, provider behavior, performance, visual quality, accessibility conformance, security clearance, production readiness, or real-client evidence. No lifecycle command creates the branch/worktree, commits, resets, cleans, or contacts a provider.

Generated link mode uses an ordinary anchor. Inline mode activates a direct cross-origin iframe near the viewport, and popup mode enhances the ordinary anchor with a native dialog and a user-activated iframe. The generated application loads no Calendly host-page script or API. Calendly account configuration, event types, provider data, cookies, retention, and provider cleanup are unmanaged. Source removal is therefore separate from provider cleanup.

The retained fixture's recurring browser specification stubs and fail-closes the Calendly origin while exercising local activation, fallback, dialog cleanup, narrow reflow, and selected axe rules. Those automated checks do not call Calendly or prove ongoing provider availability. Exact `booking-calendly@0.1.0` is certified from five reviewed current-subject outcomes: private local `fresh-scaffold` and `existing-repository-lifecycle` evidence at revision `b30e10b86b9ac9ef8dfdf1e8fa8e4077e2abe059`, plus separately bound protected-staging `deployed-application`, `provider-confirmed`, and `cleanup-recovery` evidence at revision `f9bd78f115c2118afd6dcc17ce49b2bfe34ca10d`. Prior-digest initial-scaffolding and provider receipts remain historical only. Neither evidence set establishes production readiness, ongoing provider availability, or visual quality, replaces human accessibility evaluation, or supports a WCAG conformance claim.
