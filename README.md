# Egeria Scaffold

Egeria Scaffold builds versioned, materialized Next.js recipes for Egeria Systems projects. Generated repositories remain ordinary, understandable client-owned codebases; installed capabilities, not a live profile inheritance chain, become authoritative after generation.

[ADR-0015](docs/adr/0015-vitest-five-generation.md#patched-public-generation) records the earlier patched generation and its eleven immutable successor fixtures.

## Current implementation status

The authored source candidate uses schema `2.0.0` and `portfolio@0.12.0`, `site@0.13.0`, and `app@0.3.0`. Portfolio stays one page; site provides multiple pages; app adds server foundation to the complete site experience. Generated apps pin server-only `effect@4.0.0-rc.112`. Builder-core, CLI, domain, presentation, client and content remain Effect-free.

Generation accepts capability selections. Contact uses `--contact-form-web3forms`; booking uses `--booking-calendly --calendly-mode <link|inline|popup>`; analytics uses `--cloudflare-web-analytics`, `--google-analytics-4`, `--microsoft-clarity` with its explicit audience, `--google-search-console`, and `--looker-studio` with Google Analytics selected. Destinations belong in generated environment configuration, never CLI arguments or `.egeria` settings. Multilingual, app-only persistence, transactional email and background jobs retain their independent boolean selections. The generated `docs/environments.md` and service guides own build/runtime inputs and diagnosis.

This candidate is not complete or releasable. All fourteen current subjects await separate certification renewal; generated runtime/security verification, hosted consumer reconciliation and exact visual acceptance remain open. Historical receipts cannot certify changed inputs. See the [canonical current generation boundary](docs/architecture/capability-model.md#current-environment-generation) for exact tuples, fixture identities and acceptance limits.

## App lifecycle and verification

Current add/remove/re-add supports contact, booking, analytics, multilingual and email on eligible profiles, plus app-only persistence. Email removal retains foundation. Jobs-bearing source and desired jobs lifecycle operations refuse. Ownership, surviving references, persistent-data review, clean isolated Git state, exact plan approval and state-last transaction safeguards remain in force.

The only incoming edges are `portfolio@0.12.0 -> app@0.3.0` and `site@0.13.0 -> app@0.3.0`, each over eight analytics/booking/multilingual subsets. Contact, email/retained-foundation, persistence and jobs-bearing sources refuse. Portfolio admission requires the new exact visual evidence and remains closed until approved. Site preserves its customized UI and locale values. Capability upgrades, portfolio-to-site and outgoing app transitions have no executable edge.

`verify:builder-kernel` owns the complete candidate suite. When both the kernel suite and fixed-root visual comparisons are required, run `pnpm run verify:builder-kernel -- --include-fixed-visuals` to run the fixed-root checks once with visual comparisons. `verify:generated-visuals` runs that fixed-root verification independently. `verify:app-transition-visuals` retains its separate transition matrix. These commands can install and execute generated dependencies and require their own runtime admission. Source parsing, deterministic tests and screenshot equality do not establish deployment, provider behavior, visual quality, translation quality, human accessibility or WCAG conformance.

To resume the fixed verifier, run `node scripts/verify-generated-skeletons.mjs --from-fixture=<identifier>` and include `--visual` when the run requires comparisons. The verifier checks all fixture sources for changes, executes from the named fixture through the end, and reports the fixtures it ran.

The pinned Linux verification jobs use [the CI Git helper](packages/builder-core/templates/common/application-environments/apps/web/scripts/prepare-ci-git.sh) to check both Debian package hashes before extraction and select Git for the child command. Requalify both packages and the runner image together when changing either pin.

Implementation evidence, review packets, and implementation plans are private local workflow artifacts. Git excludes them from ordinary tracking by default, and the repository contract scans tracked text for personal home-directory paths to reduce accidental machine-specific leakage.

Run the constitution contract with:

```bash
pnpm run test:constitution
```

Run the complete local compatibility proof with:

```bash
pnpm run verify:compatibility-proof
```

Run the complete approved builder-kernel gate, including deterministic fixture regeneration and isolated fixture builds, with:

```bash
pnpm run verify:builder-kernel
```

The kernel runs checks serially and continues with independent work after a failure.
It prints a private report directory at startup, then records each group's outcome,
elapsed time, repair diagnostic and log location. Where available, the diagnostic
points to a validated repository-relative test or compiler location. Private child
logs retain recognized failure categories, test counts and verifier receipt
references. They filter out raw messages and assertion values. Every required
group must pass for the command to exit successfully. On interruption, the report
preserves completed rows and identifies the interrupted and unstarted groups.

Run the narrower package, lint, build, type, and Changeset gates with:

```bash
pnpm run verify:builder-packages
```

Run the complete local public-package release-candidate gate with:

```bash
pnpm run verify:package-release-candidate
```

## Current builder topology

- `apps/cli` remains the private thin adapter for ten commands. Unsupported historical operations return stable refusals; no new command or deployment behavior is added.
