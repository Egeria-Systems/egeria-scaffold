# Builder core boundary

Read the repository [`AGENTS.md`](../../AGENTS.md), the canonical [package ownership](../../docs/architecture/package-ownership.md), and the [review and contribution protocol](../../docs/governance/review-and-contribution.md) before editing this surface.

`packages/builder-core` is the private owner of builder internals, project/state schemas, and the private certification registry contract. Its current executable boundary includes checked JSON Schema artifacts, the exact seven-capability catalog, current `portfolio` and `site` recipe `0.7.0` with readable retained `0.1.0` through `0.6.0` provenance, deterministic resolution, installed-manifest projection, strict `.egeria` codecs, subject-bound descriptor admission and closure decisions, pure hybrid-ownership fingerprint materialization, fixed-root read-only repository access, deterministic capability and surface evidence, content-safe read-only diagnostics and structural differences, deterministic in-memory rendering from explicit allowlisted templates, and state-last generation into a previously absent destination. Generation uses exact verified public package versions: standards `0.1.0` and observability `0.2.0`, with an injected verifier boundary.

- Keep runtime Zod schemas canonical and generated Draft 2020-12 artifacts byte-checked against them. Do not hand-edit artifacts.
- Keep certification records keyed by the exact executable capability identifier in [`certifications/capabilities.json`](../../certifications/capabilities.json). Bind each subject to its descriptor version and canonical descriptor/evidence-contract digest. Bind each passed evidence entry and repository-present receipt to its capability, subject, evidence-producing ancestor revision, and explicit passed and reviewed outcome. Reject incomplete, unresolved, or negatively reviewed receipts. Registry presence, admission, local evidence, or `backfill-pending` never implies certification.
- Keep descriptor admission distinct from closure. `booking-calendly`, the exact materially changed standards subject, and the explicitly amended `observability@0.2.0` subject are certified; four unchanged subjects retain frozen `backfill-pending` records. Observability certification records reviewed deployed-application and fresh-scaffold outcomes without claiming cleanup-recovery; selected retained resources remain an explicit uncertified operational disposition. Admission and transition closure pass, while all-certified closure still rejects the frozen backfills.
- Keep the executable catalog limited to `standards`, `content-files`, `section-composition`, `deployment-cloudflare`, `observability`, `site-routing`, and `booking-calendly`; keep executable profiles limited to `portfolio` and `site`.
- Keep generation package versions builder-owned, immutable, exact, and separately verified. Project-generation requests must not accept caller package versions.
- Keep reads fixed to explicitly declared control, probe, and valid-state surface paths. The reader does not enumerate or write, follows no requested-path symlink, caps text reads at 1 MiB, and emits no source content through evidence.
- Keep inference evidence separate from policy. Read-only diagnostics compose existing codecs, resolution, and inference; they neither authorize nor perform a repository change.
- Keep generation limited to the exact `src/generation` modules and checked-in `templates/common`, `templates/portfolio`, `templates/site`, and `templates/booking-calendly` allowlists. Catalog entries are explicit; do not enumerate or accept a caller-supplied template root.
- Permit only the strict caller-controlled `projectName`, `displayNameJson`, and `workerName` template tokens plus the two fixed trusted GitHub workflow-expression tokens. Permit `calendlyDestinationJson` and `calendlyModeJson` only as JSON-encoded data in `templates/booking-calendly/apps/web/src/integrations/booking-calendly/booking-settings.ts.template`. Preserve deterministic LF-normalized bytes, code-point ordering, YAML 1.2 externalized runtime copy, Markdown with validated YAML front matter as non-executable data, the source-owned typed section registry, pure presentation, and current ownership validation.
- Keep Calendly selection atomic: paired destination/mode input, exact selected-capability/settings agreement, and modes limited to `link`, `inline`, and `popup`. Accept only a maximum 2,048-character HTTPS `calendly.com` or `www.calendly.com` destination with a non-root path and no credentials, query string, fragment, normalization whitespace, or non-default port; never echo rejected values in issues.
- Keep `booking-calendly` limited to initial generation with an ordinary-link fallback and direct cross-origin iframe, enhanced with native `dialog` only for popup mode. Keep its copy, reader, client component, and browser specification application-owned, its generated settings managed, and the conditional home route builder-owned. Do not add Calendly host-page scripts or APIs, provider events, provider mutation, or later-add and existing-repository behavior. Calendly account configuration and provider data are unmanaged; source removal never implies provider cleanup.
- Keep observability's public contract provider-neutral and its generated effects infrastructure-owned. Cloudflare imports belong only in the Cloudflare adapter; browser input must remain same-origin, credential-free, referrer-free, stream-bounded before buffering, schema/vocabulary bounded, and free of raw/private fields. Keep Workers Logs custom logging explicit with invocation logs disabled, classify platform error/exception logs separately, keep version metadata explicit, Better Stack optional behind the exact two declared secrets, telemetry failures contained, analytics/storage/console interception absent, and provider/source/secret/deployment mutation outside generation. Keep source/configuration removal, credential/provider/data disposition, and recovery as separate reviewed requirements.
- Keep Tailwind CSS and PostCSS configuration, semantic design tokens, responsive presentation classes, and the global stylesheet owned by `section-composition`. Keep skip-navigation copy in validated locale content.
- Keep generated Vitest Node/jsdom packages, named projects, semantic scripts, setup, starter specifications, Playwright/axe foundation, and read-only quality workflow owned by the hybrid `standards` capability. Run `test:unit` then `test:component` after typecheck and before builds in ordinary generated-project verification. Keep browser installation explicit and browser execution outside ordinary new-project verification receipts.
- Permit repository writes only through new-directory generation into an absent leaf beneath an existing canonical parent. Write through an identity-recorded sibling temporary directory with exclusive files, require pre-state inference and injected verification, write the empty migration log and installed state last, require post-state agreement, then commit with one portable rename.
- Materialize the checked builder-owned recipe `0.7.0` lockfile byte-for-byte without resolving a new registry graph during generation. Keep subsequent verification fixed to pnpm `11.20.0`, the public npm registry, argument-array `execFile` calls, one separately owned validation copy, bounded output/time, an empty temporary home/configuration, disabled Next telemetry, and the explicit frozen-install/lint/typecheck/unit/component/Next/OpenNext command sequence. Never inherit arbitrary environment values or return child output.
- Test builder contracts with Node's test runner (`node --test`) through `pnpm run test:builder-core`; use `pnpm run test:generated-project` for production generation and the fixed verifier for retained fixture/browser certification. Generated Vitest starter behavior is tested through the rendered project, not by migrating builder-core tests to Vitest. Add `fast-check` only in the later approved state/migration increment with reproducible seed/path evidence.
- Treat portable rename as a narrow commit boundary, not a hostile-concurrency no-clobber guarantee: another process can create the destination after the final absence check on platforms where rename replaces an existing target.
- Do not add existing-repository transformation, clean-Git policy, migration execution, recovery automation, provider API integration, CLI behavior, or later-stage capability runtime code.
- Do not create or move schema ownership into a separate `project-schema` package.
- Do not expose builder-core as a public package or add generic `PlatformService` or `ApplicationDatabase` ports.
- Follow the currently approved increment and stop at its review gate before expanding this boundary.
