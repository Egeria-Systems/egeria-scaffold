# `@egeria-systems/builder-core`

Private ownership boundary for Egeria Systems builder internals.

Builder-core owns executable runtime contracts for capability descriptors, profile recipes, desired project configuration, installed state, and successful migration records. Zod schemas are canonical; checked Draft 2020-12 artifacts live in `schemas/`. After building builder-core, regenerate them with `pnpm run schema:generate` or verify them without writes using `pnpm run schema:check`; `pnpm run verify` runs the required build first.

Builder-core also owns the private certification registry schema, canonical subject digest, repository-artifact validation, descriptor admission, and closure policies consumed from [`certifications/capabilities.json`](../../certifications/capabilities.json). Admission requires exact coverage for every executable descriptor, rejects stale versions or behavior-contract digests, and validates that referenced plans and evidence exist and that evidence metadata binds its capability, subject, evidence-producing ancestor revision, and explicit passed and reviewed outcomes. It rejects incomplete, unresolved, or negatively reviewed receipts. Closure is separate: `booking-calendly@0.1.0` now satisfies the current transition policy, which exempts only the six frozen pre-foundation identifier/version/digest subjects; all-certified closure still rejects those six non-certified records. Neither admission nor local evidence by itself means a capability is certified.

The runtime Zod schemas are authoritative for repository validation. The checked Draft 2020-12 artifacts are byte-current structural contracts and can be broader or less restrictive where the current Zod-to-JSON-Schema conversion cannot represent a runtime refinement. Consumers that require the complete contract must use the runtime schemas; schema currency does not claim full semantic parity between the checked artifacts and every runtime refinement.

The catalog boundary owns the exact seven executable capability descriptors for `portfolio` and `site`, their current materialized recipe `0.5.0`, readable retained `0.1.0` through `0.4.0` provenance, deterministic dependency-first resolution, and projection into installed-capability manifest entries. `booking-calendly@0.1.0` is the only optional initial-scaffolding capability; it depends on `section-composition` and does not change either recipe default. Generation uses immutable, separately verified `0.1.0` versions for the public standards and observability packages. Calendly adds no package. Public package probes require exact stable versions; workspace, file, Git, URL, range, tag, and prerelease specifications are rejected without being echoed in issues.

The state and ownership boundary owns strict YAML 1.2 `project.yaml`, JSON `state.json`, and successful-record JSONL migration codecs. Calendly selection and its strict destination/mode settings must be present together; existing empty capability settings remain valid. The booking copy, reader, client component, and browser specification are application-owned, its generated settings are managed, and the conditional home route is builder-owned. The boundary also owns deterministic SHA-256 fingerprints over exact file bytes or canonical RFC 6901-selected JSON values and pure descriptor-to-installed-surface materialization. These APIs do not create or read repository files.

The repository-inference boundary owns fixed-root read-only text access and deterministic capability and surface evidence. Filesystem reads reject unsafe paths and requested-path symlinks, require regular files beneath a non-symlink root, cap content at 1 MiB, and require valid UTF-8. Inference reads only `.egeria/state.json`, catalog-declared probes, and valid-state managed surfaces; it returns stable metadata and codes without actual repository values or source content.

The diagnostic boundary owns `doctorRepository` and `diffProject`. Each operation reads the required `.egeria` control files, declared probes, and valid-state managed surfaces through one per-operation cache. Doctor returns stable codes for invalid control contracts and desired, installed, inferred, or surface disagreement. Diff returns explicit structural difference kinds. Neither API returns source content, writes a repository, authorizes a transformation, or claims that a repository is safe to change.

`renderSkeleton` performs deterministic in-memory rendering from explicit allowlisted templates for the `portfolio` and `site` recipes, keeps structured, skip-navigation, and booking copy in validated YAML 1.2 files and Markdown with validated YAML front matter as non-executable data, renders only the four source-registered typed section shapes, and emits a responsive pure Server Component interface. The `section-composition` capability owns Tailwind CSS and PostCSS package properties, PostCSS configuration, semantic global design tokens, and responsive presentation source. The hybrid `standards` capability owns generated Playwright and axe packages, explicit browser-install and environment-specific scripts, shared/development/preview/deployed configuration, a content-agnostic browser-quality specification, and a read-only immutable quality workflow.

When explicitly selected, `booking-calendly` accepts only paired strict settings: `link`, `inline`, or `popup` plus a bounded HTTPS `calendly.com` or `www.calendly.com` destination with a non-root path and no credentials, query string, fragment, normalization whitespace, or non-default port. Link mode remains an ordinary anchor. Inline mode activates a direct cross-origin iframe near the viewport; popup mode enhances the ordinary anchor with a native dialog and user-activated iframe. The generated source loads no Calendly host-page script or API. Rendering returns the validated desired project, resolution, sorted file bytes, and ownership descriptors and reports stable sanitized failures without rejected destinations.

`generateProject` owns bounded creation of one previously absent destination. It injects the immutable verified package versions, writes rendered files and project configuration exclusively in an identity-recorded sibling temporary directory, accepts only one new regular lockfile from the injected verifier, requires probable pre-state inference, delegates isolated verification, writes an empty migration log and validated installed state last, requires confirmed post-state inference with no managed drift, and commits with one rename. Failures clean only an identity-matching source temporary directory. The verifier is an effect boundary; it owns no catalog, state, or lifecycle decision.

`createPnpmGeneratedProjectVerifier` is the concrete effect adapter. It requires pnpm `11.20.0`, prepares the lockfile with scripts disabled and a builder-owned external store, copies the source into a separately owned validation directory, and runs the frozen install, lint, typecheck, Next build, and OpenNext build there. Child processes receive only a narrow platform/process environment, a blank home and npm configuration, the public npm registry, and disabled Next telemetry. Commands use argument-array `execFile` calls with bounded time and output; child output is never returned. Validation and support owners are identity-checked before recursive cleanup.

Portable filesystem rename does not provide a hostile-concurrency no-clobber guarantee on every supported platform. Generation checks destination absence immediately before rename and preserves destinations observed before that check; a target created after the check may still be replaced where the platform's rename semantics permit it.

The retained `portfolio-calendly` popup fixture is the representative selected-capability proof. The fixed-root verifier regenerates it, checks desired/installed/inferred agreement, builds it in an identity-bounded copy, and executes its browser specification against a stubbed and fail-closed provider origin. The fresh-scaffold certification runner separately creates the same bounded selection through the compiled CLI, re-infers it, requires healthy diagnostics and an empty exact diff, and passes that actual output to the shared fixed-root verifier. Those repeatable checks do not establish Calendly availability or a real booking. A separate exact-revision provider receipt records the protected-staging, booking, confirmation, cancellation, and cleanup evidence that certifies `booking-calendly@0.1.0`. Neither evidence set establishes visual quality, human accessibility, production readiness, or WCAG conformance. Calendly account configuration and provider data are unmanaged, and source removal is separate from provider cleanup.

Existing-repository transformation, clean-Git enforcement, migration execution, persistent-data rollback, provider configuration/action/cleanup, recovery automation, and every later capability remain outside this increment. The private CLI is the current thin consumer of generation, inference, and diagnostics; it owns no builder decisions. A separate project-schema package is intentionally absent.

The canonical API and lifecycle owner is [package ownership](../../docs/architecture/package-ownership.md).
