# `@egeria-systems/builder-core`

Private ownership boundary for Egeria Systems builder internals.

For the production-site candidate, exact descriptor admission passes while both closure policies intentionally remain blocked by pending `site-routing@0.4.0`. Historical references below to `all-certified` closure passing describe only the accepted `site-routing@0.3.0` baseline and do not certify the successor subject.

Builder-core owns executable runtime contracts for capability descriptors, profile recipes, desired project configuration, installed state, and successful migration records. Zod schemas are canonical; checked Draft 2020-12 artifacts live in `schemas/`. After building builder-core, regenerate them with `pnpm run schema:generate` or verify them without writes using `pnpm run schema:check`; `pnpm run verify` runs the required build first.

The runtime Zod schemas are authoritative for repository validation. The checked Draft 2020-12 artifacts are byte-current structural contracts and can be broader or less restrictive where the current Zod-to-JSON-Schema conversion cannot represent a runtime refinement. Consumers that require the complete contract must use the runtime schemas; schema currency does not claim full semantic parity between the checked artifacts and every runtime refinement.

The state and ownership boundary owns strict YAML 1.2 `project.yaml`, JSON `state.json`, and successful-record JSONL migration codecs. The state schema remains `1.0.0` and includes the exact `lastSuccessfulVerification.kind` values `capability-upgrade` and `profile-transition` without changing project or migration schema `1.0.0`. The boundary also owns deterministic SHA-256 fingerprints over exact file bytes or canonical RFC 6901-selected JSON values and pure descriptor-to-installed-surface materialization. These APIs do not create or read repository files.

The repository-inference boundary owns fixed-root read-only access and deterministic capability and surface evidence. Filesystem reads reject unsafe paths and requested-path symlinks, require regular files beneath a non-symlink root, and cap content at 1 MiB; text reads additionally require valid UTF-8. The profile-transition planner uses bounded exact byte reads only for its seven declared action subjects so binary visual baseline drift is not hidden by text decoding. Inference reads only `.egeria/state.json`, catalog-declared probes, and valid-state managed surfaces; it returns stable metadata and codes without actual repository values or source content.

The diagnostic boundary owns `doctorRepository` and `diffProject`. Each operation reads the required `.egeria` control files, declared probes, and valid-state managed surfaces through one per-operation cache. Doctor returns stable codes for invalid control contracts and desired, installed, inferred, or surface disagreement. Diff returns explicit structural difference kinds. Neither API returns source content, writes a repository, authorizes a transformation, or claims that a repository is safe to change.

The addition lifecycle boundary owns bounded Git inspection, `planCapabilityAddition`, and `applyCapabilityAddition` for `booking-calendly@0.1.0`. Planning requires a clean attached linked worktree and treats tracked changes, all non-ignored untracked files, and the `assume-unchanged` and `skip-worktree` index flags as dirty. It requires the installed state to match the exact canonical managed-surface inventory and every installed application-owned surface to remain a readable regular file, without comparing application-owned content fingerprints. It refuses active Git operations, conflicts, managed drift, missing surfaces, ejections, present create-target collisions, absent but Git-ignored create targets, unexpected Git/reader failures, and identity changes, then derives deterministic actions from the current and desired renders. Its approval-required result redacts settings and repository metadata except for the intentional base revision and binds the full private input plus exact Git identity into a deterministic fingerprint.

Application accepts only that exact fingerprint in the same eligible worktree. It stages same-directory expected-content writes for the seven planned actions, revalidates content and identities before atomic replacement or exclusive installation, verifies a VCS-metadata-free separate copy, requires the exact pending-add inference and transformed bytes, appends one successful migration record, persists state last, requires final state/inference and the exact dirty paths, and then rereads exact migration, state, and source bytes as the final awaited check before stopping for verified-final-diff approval. Persisted receipts list only checks completed before persistence; the returned success result adds migration-record and post-state-inference checks. Before a write, failure requires no recovery. After a write, failure preserves the isolated worktree prefix for explicit inspection; it never resets, cleans, commits, creates a branch/worktree, auto-rolls back, or contacts a provider.
