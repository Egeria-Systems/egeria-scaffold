## Dependency direction

- The CLI and builder-core depend on standards only for development-time compilation. Builder-core uses Zod for runtime validation and YAML for its strict in-memory project codec. The CLI may depend on builder-core only after an approved executable CLI stage creates a concrete need.
- Observability depends on standards only for development-time compilation and has no runtime dependencies.
- The builder root uses ESLint `10.9.0` for `apps/cli` and builder-owned source under `packages/*`. The strict type-aware factory applies to TypeScript source; standards configuration source uses the same root's core recommended rules. The root also consumes the pending copy-externalization source API for canonical builder application, presentation, and section TSX templates without changing generated dependency graphs.
- Standards declares and behaviorally tests both ESLint `9.39.5` and `10.8.0`. Dual-major package support does not imply that the accepted P0.2 proof migrated.
- The compatibility proof remains an independent ESLint `9.39.5` and Next configuration consumer. Future generated Next.js projects retain ESLint `9.39.5` while their selected Next plugin graph requires it and must revalidate that graph before changing majors.
- The strict lint factory pins `typescript-eslint` because its strict presets are not semver-stable, enables project-service typed linting, and leaves formatting ownership outside ESLint.
- The repository-local semantic-naming matcher and scanner are the permanent enforcement owner. Semantic naming is not a standards export or public package API. See the [enforcement map](enforcement-map.md).
- Builder-core's core infrastructure and consuming-boundary ports remain provider-neutral; its allowlisted generated application templates may be provider-specific. Builder-core does not depend on the CLI.
- `booking-calendly` remains generated application source within builder-core's allowlisted templates. It adds no public package, provider adapter, host-page script, API client, secret, environment variable, or platform resource. The [capability model](capability-model.md) owns its exact state, surface, inference, security, verification, and removal contract.
- `multilingual` remains generated application source within builder-core's explicit locale overlay templates. It adds no public package, provider adapter, secret, environment variable, external domain, platform resource, persistent data, analytics, or deployment behavior. The [capability model](capability-model.md#executable-multilingual-boundary) owns its exact locale, routing, content, composition, lifecycle, certification, and claim limits.
- `analytics` remains generated application source within builder-core's explicit analytics templates. Cloudflare Web Analytics, Google Analytics 4, and Microsoft Clarity have separate runtime loaders and purposes; Search Console and Looker Studio remain operational integrations. Provider-facing generated source is allowed only inside that boundary. No analytics package, event bridge, or provider selection is added to observability. The [capability model](capability-model.md#executable-analytics-boundary) owns consent, provider, security, lifecycle, certification, and claim limits.
- Public packages remain ordinary replaceable dependencies. Public availability does not transfer ownership of generated application code back to this repository.
- Cloudflare types and bindings remain in platform adapters and composition roots; no package may hide them behind a generic platform or database service.

## Versioning and release boundary

Exact `0.1.0` and `0.2.0` releases of both public packages and `@egeria-systems/observability@0.3.0` are available on npm. The immutable bootstrap `0.1.0` releases have registry signatures but no provenance attestations under their approved one-time exception. Both `0.2.0` releases and observability `0.3.0` were published through npm OIDC trusted publishing with explicit provenance and have registry signatures and attestations. Public availability and installed capability selection remain separate: generated projects install standards `0.1.0` and observability `0.3.0`. The repository-level Changesets default remains restricted, and private-package versioning and tagging are disabled.

Changesets owns package versioning and publication. The manual workflow delegates to Changesets and does not create another release resolver. Package-boundary tests enumerate the only locally publishable packages and execute dry-run packs to enforce exact public tarball contents. Release-context and registry tests fail closed unless the manual [package release workflow](../../.github/workflows/package-release.yml) receives an exact commit on `main` and each public package matches its approved exact registry history and expected target status: an unchanged version remains present, while a new target version remains absent.

The manual `package-release.yml` job uses the protected `npm-release` environment and accepts only an exact `main` commit supplied to `workflow_dispatch`. The bootstrap token has been removed and revoked. The `0.2.0` releases and observability `0.3.0` exercised npm OIDC trusted publishing and the workflow's explicit provenance request, `NPM_CONFIG_PROVENANCE: "true"`, after full verification and a final exact registry-history gate. Authentication cleanup is unconditional. The workflow publishes packages only; it contains no application deployment or push path. Local configuration and a green workflow never authorize publication or deployment. npm namespace control, licensing, rights, credentials, exact package contents, provenance, and each external publish command require separate current evidence and explicit human approval under the [review and contribution protocol](../governance/review-and-contribution.md).
